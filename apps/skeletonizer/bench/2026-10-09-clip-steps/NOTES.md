# 2026-10-09 shimmer 降频（steps）实验：clip 默认文字模式能省多少重绘

实验性质：没有改 `src/`、README、docs，所有 CSS 变体都叠在现成的 `dist/` 之后（`exp/*.css`）。

## 假设

global 方案的光带位置由根上一个 CSS 动画驱动注册过的 `--skz-shimmer-p`。样式重算每帧都会被动画触发（上一轮已测过，`steps()` 对"重算事件"本身没用）。**假设**：重绘只在计算值真正变化时才发生，所以把光带降到 24 / 12 次每秒后，值不变的帧不用重画文字遮罩（clip）和骨头背景，clip 的 Paint / GPU / PrePaint 应该按比例下降。

## 结论（一句话版）

- **成立，但有个前提**：值不变的帧确实不重绘。clip 默认模式下，每秒有绘制的帧数 60 → 24 → 12，Paint 事件数、RasterTask 数、GPU ms 都跟着掉（GPU 11.4 → 2.8~3.0 → 1.3~1.5 ms）。
- **前提是 shimmer 时一起跑的 pulse 动画不能让别的值逐帧变**：clip 模式下 pulse 只改 `--skz-ul-fill`，而 clip 把所有后代的装饰线颜色设成透明，所以 pulse 对画面零贡献（冻结同一时刻截图逐字节一致，见下），也不触发重绘，**但它仍然让样式重算每帧都做实事**。去掉 pulse（或同样降频）后，steps 才能把样式重算也一起省掉（2000 卡 7.2 → 2.6 ms，4× 降速下 19.6 → 47.2 fps）。
- **underline 模式不一样**：pulse 驱动下划线颜色，它每帧都在变色，所以 underline + steps(pulse 原样) 只能把有绘制的帧降到 ~55~69%；pulse 也 steps 之后才降到 40% / 20%。
- **svg 引擎**：SMIL 加 `calcMode="discrete"` 可以做（改生成的 SVG 文本即可），屏幕上光带确实按 24 / 12 次每秒跳；GPU / Raster 随之降（5.6 → 3.0 → 1.5 ms），但 **clip + svg 下 Paint 事件仍是每帧一次（120/s 不降），PrePaint ms 只降 10~19%**，不是按比例降。4× 降速下 svg 完全没改善。

## 方法

- 沿用 `../2026-10-09-clip-default/` 的基准页（`perf.html` 在其上加了实验开关）、`bench/kit/run-locked.mjs` 加锁串行、自带的 `trace.mjs`（kit 版的增强，见下）采集。视口 1200×800、DPR 1、Chrome 154、Windows、60Hz 显示器；端口 9611，配置目录 `C:/Users/jelon/AppData/Local/Temp/skz-steps-chrome`。
- 页面全部取 `pnpm build` 产出的 `dist/`（本次没重新构建：`dist/` 的时间戳 22:05，晚于所有 `src/styles` 与 `src/*.ts` 的改动；`dist/global.css` sha1 `2710225c…`、`dist/index.mjs` sha1 `2727f0f7…`）。为避免别处重新构建影响基准，先把 `dist/` 整个拷到 `Temp/skz-steps-dist/`，由本目录 `serve.mjs`（静态服务，端口 5192）的 `/dist/` 指向那份快照。没有走 5188 的 Vite dev 服务。
- 场景全部走真实 `enable(root, { effect: "shimmer" })`（含继承防火墙：500 卡 fw=492 项，视口内只有 ~6 张卡）；clip = 默认，underline = `text:"underline"`。
- 每个场景 3 次 trace（各 2.5 秒）取中位数；每批首尾各一对金丝雀（shimmer lin clip @500、fade @2000）；同变体 clip / underline 相邻放置。每批测前等整机 CPU 安静（<15% 连续 6 秒，最长 10 分钟；这台机器常驻后台负载 12~18%，多半等到超时才开跑），批均值超过阈值整批重跑。
- 实验 CSS：只覆盖根上 `animation`，选择器 `[skz][skz-effect="shimmer"]` 与 `dist/global.css` 同优先级、靠加载顺序胜出；`--skz-duration` 默认 1.5s（探针读到 `1.5s steps(36) infinite skz-shimmer-root, 1.5s ease-in-out infinite alternate skz-pulse-root`）。

| 变体 | shimmer 时间函数 | pulse（`skz-pulse-root`） | 光带每秒变化次数（探针实测，未降速的场景） |
|---|---|---|---|
| lin | linear | 原样 ease-in-out alternate | 59~60 |
| s36 | steps(36) | 原样 | 23.5~23.9 |
| s18 | steps(18) | 原样 | 11.5~12 |
| *-nop | 同上 | 不跑（动画列表里去掉） | 同上 |
| s36-ps / s18-ps | 同上 | 也改 steps(36) / steps(18) | 同上 |

- 对 `trace.mjs` 的增补（相对 `bench/kit/trace.mjs`）：
  - 每秒事件数：`nPaintPS`（主线程 Paint 事件）、`nPrePaintPS`、`nUpdateLayoutTreePS`、`nCommitPS`、`nRasterPS`（`ThreadPoolForegroundWorker` 上的 `RasterTask`）、`nGpuTaskPS`；
  - `paintFramesPS`：把相距 <8ms 的 Paint 事件归为同一个"有绘制的帧"（一帧里常有 2 个 Paint 事件：lin 下 120 事件/s = 60 帧 × 2），折算每秒有绘制的帧数；占比 = `paintFramesPS / fps`；
  - `probe`：场景里写 `probe:true` 时，trace 前每帧读一次根上 `--skz-shimmer-p`（会触发强制样式重算，所以不在 trace 内做），统计每秒变化次数，证明实验 CSS 真的生效。
  - 原 kit 里 `raster` 取的是 `CompositorTileWorker` 线程，本机 Chrome 154 的光栅在 `ThreadPoolForegroundWorker`，所以那一列恒缺；本批新增 `rasterMs` 补上。
- 观感取证（`frames.mjs`）：CDP `Page.startScreencast` 抓 2 秒连续帧（合成器出新帧才会有帧）+ 每个 rAF 记一次 `--skz-shimmer-p`。
- 等价性核对（`equiv.mjs`）：用 Web Animations API 把所有动画暂停到 `currentTime=450ms`，比较"带 pulse"与"不跑 pulse"的截图 PNG 字节。

读法：

1. **clip 下 pulse 不触发重绘**：A 批 clip s36 的有绘制帧 24.4/s，和 B 批 `-nop` / `-ps` 的 24/s 一样（pulse 原样时 Paint 事件 48.8 vs 去掉后 48，没差）。
2. **但 pulse 让样式重算每帧都做实事**：2000 卡 s36 的样式重算 6.39 ms，去掉 pulse 后 2.56 ms（−60%），pulse 也 steps 后 2.56 ms；lin 下去不去 pulse 都是 ~7.2（光带本来就每帧变）。500 卡 2.27 → 0.83。`nUpdateLayoutTreePS` 仍是 60.4/s（动画每帧都触发一次重算事件），值没变的帧里那次重算几乎是空操作，所以均摊 ms 才降。这和上一轮"steps 对样式重算无收益"并不矛盾：那时 pulse 还在逐帧变值。
3. **underline 下 pulse 就是重绘源**：下划线颜色随 pulse 变，pulse 原样时有绘制帧只降到 69% / 56%（8 位颜色量化，慢段有些帧值没变）；去掉 / 降频 pulse 才到 40% / 20%。**注意 `-nop` 在 underline 下会让下划线颜色不再脉冲，画面不等价**（`equiv.mjs`：underline 两张截图 sha1 不同），所以 underline 的可比方案是 `-ps`。

## 观感（`frames/`）

- 光带 `--skz-shimmer-p` 从 -60 走到 110（共 170vw，每周期 1.5s），背景渐变宽 60vw（`--skz-bg-size: 60vw 100vh`）。**每步位移 = 170vw / N**：

| 档位 | 每秒变化 | 每步 | 每步停留 | @390px（手机） | @1200px（本次） | @1920px |
|---|---|---|---|---|---|---|
| linear（60Hz 下每帧） | 60 | 1.89vw | 16.7ms | 7.4px | 22.7px | 36.3px |
| steps(36) | 24 | 4.72vw | 41.7ms | 18.4px | 56.7px | 90.7px |
| steps(18) | 12 | 9.44vw | 83.3ms | 36.8px | 113.3px | 181.3px |

  每步相当于光带宽度（60vw）的 7.9%（24/s）/ 15.7%（12/s）。steps 是 jump-end，最高只到 -60 + 170 × (N-1)/N，一个周期末尾不会停在 110。
- 实测：探针读到每步 4.72vw / 9.44vw / 1.89vw，每秒变化 23.5~23.9 / 11.5~12 / 58.6~59.8 次（`results/*.jsonl` 的 `probe`；4× 降速场景里 rAF 本身只有 ~20 fps，探针次数会受限于帧率，不用来取证）；screencast 合成帧率 59.5 / 24.5 / 12.5 每秒，说明屏幕确实只在步点上换画面（`results/frames.log`）。
- 拼图：
  - `frames/waterfall-all.png`（lin / s36 / s18 自上而下）：每行是一个 1/60 秒时刻、第 1 张卡片段落条（放大了对比度）；连续光滑的斜边 vs 24/s 的小台阶 vs 12/s 的大台阶，可以直接看出量化程度。
  - `frames/waterfall-{lin,s36,s18}.png`（单个变体）；原始帧序列在 `frames/{lin,s36,s18,svg-nat,svg-d36,svg-d18}/f*.jpg`（只保留光带在条内的 ~0.7s 窗口，序号是原始序号；`manifest.json` 是每帧相对首帧的毫秒，`p.json` 是 rAF 级 [毫秒, p] 采样，`frames/analysis*.json` 是从像素量出的光带中心位置序列）。
  - 从像素量出的"光带中心位移"（段落条内亮度质心）只有名义位移的 ~0.4 倍（9.4 / 20.6 / 48.1 px，svg：12.5 / 24.4 / 55.6），因为条只有 710px、光带 720px 宽且被裁，质心的移动被压缩；这个数只用来看各档之间的比例（约 1 : 2.2 : 5.1，名义 1 : 2.5 : 5），**px 的绝对值以上表的名义位移为准**。
- 主观感受：**没有做真人观感测试**，我只能描述客观量化：24/s 是电影帧率，每步 4.7vw、停留 42 ms；12/s 每步 9.4vw、停留 83 ms，光带宽 60vw、边缘本身是渐变，所以台阶感主要出现在光带亮核心的边缘（窄屏更不明显，宽屏每步近 180px）。判断"能不能接受"需要人在真机上看。

## 没验证的

- 只测了 Chrome 154 / Windows / 60Hz / DPR 1 / 1200×800。Firefox、Safari 对"计算值不变不重绘"的处理没测；高刷屏（120/144Hz）没测（lin 在高刷下每帧都画，预期降频收益更大，但没数据）。
- 4× 降速只降主线程，GPU 没降；没上真机低端机。
- 没做真人观感评审；steps 的 N 与 `--skz-duration` 绑定（N 固定为 36 时，换 duration 频率就变了），`steps(calc(var(--x) * 24))` 之类能否跟随 duration 自动换算没试。
- clip + svg 下 Paint 为什么不随降频降，没做根因验证。
- 只测了亮色主题的等价截图（一个冻结时刻）；深色、其他 pulse 时刻没测。
- `effect: "pulse"` 单独的路径（没有 shimmer）没测降频。
