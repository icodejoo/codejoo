# 2026-10-10 core 实测与规模上限

对象：拆成 core + 完整版之后的 **core**（`import "skeletonizer"`：`core-js.mjs` + `core.css`）在它的目标规模（单个根约 2000 元素以内）里的表现，以及超过多少元素该换完整版。对照：同规模的完整版（`skeletonizer/global`：`base.css` + `global.css` + `full.mjs` + `global-js.mjs`，带继承防火墙）。第 1 批（JS 拆分）、第 2 批（CSS 分层）已在工作区，本批只测、写文档，没有改 `src/`（除了 `explicit.css` 恢复懒渲染规则，见下）。

**两个问题的答案**（数据在下面，文档里的版本见 README「core 的规模上限」）：

1. **core 在约 2000 元素内 pulse / shimmer 是否稳定 60 帧？** 桌面级 CPU、正常速度：是（1000 / 2000 元素 60.4 帧，4000 元素 pulse 59.2 / 58.4、shimmer 60.4 / 60，两次整批测量）。**4× CPU 降速（慢设备的粗略替身）：否**，2000 元素 pulse 21.2 / 18、shimmer 17.2 / 16 帧，504 元素也只有 40.8 / 52 帧。
2. **超过多少元素建议换完整版？** 桌面级 CPU：pulse 超过约 4000 元素、shimmer 超过约 6000 元素开始掉帧（6000 元素 pulse 46.4~49.2、shimmer 58~60.4；8000 元素 34.8~39.6 / 41.2~52.4；12000 元素约 25 / 24；16000 元素约 18~19 / 15~17），建议约 4000 元素就换。慢设备（4× 降速）：504 元素已经不到 60 帧，门槛低得多。完整版同条件：正常速度到 16000 元素都是 60.4 帧；4× 降速 2000 元素 55~60 帧、4000 元素 pulse 39~48 / shimmer 46~58 帧。

## 环境与方法

- 机器：Windows 10 桌面，Intel i5-13500 + UHD 770 集显；Chrome 154.0.8037.98（独立用户目录 `C:/Users/jelon/AppData/Local/Temp/skz-core-chrome`，CDP 端口 9711，前台窗口），视口 1200×800、DPR 1；**只有 Chrome**。
- 被测产物：`pnpm build` 的 `dist/` 冻结成快照（`C:/Users/jelon/AppData/Local/Temp/skz-core-dist`），由 `serve.mjs`（端口 5211，`/d/` 指向快照）提供，**不走 5188 的 vite 开发服务**。基准页 `perf.html` 用 import map 把 `skeletonizer` 指到 `core-js.mjs`（core）或 `full.mjs` + `global-js.mjs`（完整版），样式按 `<link>` 引 `core.css`（core）/ `base.css` + `global.css`（完整版）——和"无打包器"的真实用法一致。
- 场景：每张卡 8 个元素（卡片容器、头像图、内容容器、标题、段落、标签 span、图标、按钮），125 / 250 / 500 卡 ≈ 1000 / 2000 / 4000 元素；`enable(root, { effect })` 走真实路径，默认文字模式 clip。快照里记录 `skz-effect` / 根动画名 / `skz-fw` 数量（core 为 0，完整版 ≈ 卡数）和 shimmer 的 `--skz-shimmer-p` 变化频率（降频后约 24 次/秒，过载时低于它）。
- 每格**新鲜加载页面**（场景的 `css` 里带无意义令牌 `f<序号>`，强制 `Page.navigate`），避免 `../2026-10-10-layering/NOTES.md`「会话状态陷阱」；3 次 trace（每次 2.5 s）取中位数；"开启"是真实 `enable()`（再加一次强制样式 + 布局）的耗时，5 次中位数，波动大，只当量级看。
- 并发：`bench/kit/run-locked.mjs` 加锁串行；`run-batch.mjs` 先 `wait-idle.ps1` 等整机 CPU 连续 6 秒 <15%（最多 180 秒），后台 `cpu-log.ps1` 采样批内整机 CPU；批均值超过 32% 就整批重跑（最多 3 次，取均值最低的一次）。
- 4× 降速：场景里写 `cpu: 4`，`Emulation.setCPUThrottlingRate`，测完复位；不是真机。

## 机器负载（不是安静状态）

日常工作机，后台常驻负载使整机 CPU 空闲基线约 22%~24%（每次 `wait-idle` 都等满 180 秒超时，没有拿到 <15%；`after2` 那次测前均值 31.1%）。批均值里**含被测 Chrome 自己的占用**（大页面本身就吃 CPU），没有拆开。

| 批 | 尝试 | 测前 CPU（idle 等待超时时的均值） | 批内整机 CPU 均值 / p90 / 最大（%） | 采用 |
| --- | --- | --- | --- | --- |
| M `after`（主批） | 1 | 24.4 | 31.2 / 42.4 / 88.8 | 是（≤ 32% 阈值，首次通过） |
| M `after2`（整批复跑） | 1 | 31.1 | 30.8 / 38.7 / 97.2 | 复跑，数据单列 |
| T `after`（上限批） | 1 | 22.5 | 35.8 / 49 / 83.5 | 否 |
| T `after` | 2 | 23.1 | 33.7 / 41.9 / 95.6 | **是（三次里均值最低）** |
| T `after` | 3 | 23.7 | 34.8 / 44.4 / 98 | 否 |

T 批三次都超过 32% 的阈值（页面越大 Chrome 自己占用越高，阈值对 6000~16000 元素的批偏严），按规则取均值最低的第 2 次，另两次的数据保留，三次之间互相吻合（见下）。

## 结论

1. **core 在约 2000 元素内 pulse / shimmer 稳定 60 帧吗？**
   - 桌面级 CPU、正常速度：**是**。1000 / 2000 元素三个效果的 fade / solid / pulse / shimmer 都是 60.4（solid 60.4~60.8）帧；4000 元素 fade / solid 60.4~60.8、shimmer 60.4（复跑 60）、pulse 59.2（复跑 58.4）。pulse 的样式重算随元素数近似线性，约每 1000 元素 2.9 ms（3.05 / 6.18 / 11.56 ms），4000 元素已经逼近 16.7 ms 的帧预算；shimmer 约每 1000 元素 1.3 ms（1.27 / 2.61 / 5.05 ms）。
   - 慢设备（4× 降速，粗略替身）：**否**。core 2000 元素 pulse 18~21 / shimmer 16~17 帧，1000 元素 28~32 / 18~27 帧，504 元素 41~47 / 42~52 帧（更小规模没测）。同条件完整版 2000 元素 55~60 帧。core 的 fade / solid 没在 4× 降速下测。
2. **超过多少元素建议换完整版？** 以"稳定 60 帧"为线：桌面级 CPU 上 pulse 约 4000 元素、shimmer 约 6000 元素；保守给使用者 2000 元素留一倍余量，**建议超过约 4000 元素换完整版**。要照顾慢设备，线要低得多（几百元素就破线，没测更小规模），要么单根很小、要么换完整版、要么 core 里只用 fade / solid。依据：上表 M / T 批 core 与完整版同规模对照（完整版 6000~16000 元素全 60.4 帧，样式重算 1.1~6.8 ms）。
3. 这条线随 CPU 算力按比例平移：样式重算毫秒数随元素数线性增长，所以"约 4000 元素"只对本机这类桌面 CPU 成立。
4. 完整版同样有限：4× 降速下 4000 元素 pulse 掉到 39~48、shimmer 46~58 帧。
5. 降频生效：core shimmer 的 `--skz-shimmer-p` 变化频率正常约 24 次/秒（`1.5s steps(36)`），元素多了主线程过载就掉到 20（12000）、17（16000）、6（4× 降速 4000 元素）次/秒。
6. 开启耗时（`enable()`）：core 125 / 250 / 500 卡约 5~8 / 9~15 / 18~25 ms（与完整版同量级），16000 元素约 70~100 ms；`after2` 复跑同量级。

## 没做 / 没验证

- 没有 Firefox / Safari / 真机；"4× 降速"只是 CDP 的 CPU 降速。
- core 的 fade / solid 没在 4× 降速下测（完整版同基底 fade 的 4× 数据见 `docs/reports/2026-10-09-benchmark-matrix.md`）。
- 4× 降速下更小规模（< 504 元素）没测，所以"慢设备 core 的 pulse / shimmer 的安全元素数"只知道 504 元素已经不到 60 帧。
- 没测深色模式、没测 underline / tofu / svg（core 没有这些）；没测 `fit`。
- 整机 CPU 不是安静状态（批均值 30.8%~35.8%），4× 降速的格子波动大；差距在 10% 以内的别当真。
- 没有和第 2 批 NOTES 里 core 页面预览（2000 卡 = 16000 元素，pulse 约 23 帧 / shimmer 约 21 帧）逐格对账：本批 16000 元素 pulse 18.4 / shimmer 16.8 帧，机器负载不同，量级一致。

## 顺带：`explicit.css` 恢复懒渲染规则

第 2 批把 `skz-paused` / `skz-cv` 规则从 `explicit.css` 里去掉了；本批按用户的决定放回（`explicit.css` += `_lazy`），让"`explicit.css` + 完整版 JS"组合有懒渲染；`core.css` 仍不含。体积（gzip -9 -n）：`explicit.css` 3312 → 3518 B raw、1000 → 1062 B gzip（0.98 → 1.04 KB）。`test/styles.test.ts` 的断言同步更新（explicit 含 `skz-paused` / `skz-cv`，core / global / svg 不含）。
