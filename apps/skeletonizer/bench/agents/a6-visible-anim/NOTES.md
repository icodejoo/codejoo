## 1. 方案

根 `[skz]` 不跑动画（CSS：根带 `skz-a` 时 `animation:none`，变量保持静态）；JS 用一个共享 IntersectionObserver（rootMargin 200px，同防火墙）观察列表项：
- 进入：打 `skz-anim`，CSS 在这个项上挂 `skz-pulse-root` / `skz-shimmer-root` 动画，并在项上重新声明派生变量（`--skz-fill` / `--skz-ul-fill` / `--skz-bg-pos`，因为根上它们已用 var() 展开成具体值）。
  然后**第二遍**对这些项 `getAnimations()` 并 `a.startTime = 0`，所有可见项按 `document.timeline` 同一条时间轴取相位，和进入时刻无关。
- 离开：撤掉 `skz-anim`，动画消失，该项只继承根上的静态值。
- 列表项定位复用 `firewallItems`；MutationObserver 盯列表容器的子节点增删，新项自动纳入。
- 找不到列表项（<2 个）时不打 `skz-a`，根照旧自己驱动（CSS 靠 `[skz-a]` 门控，**这一条没实测，按规则推断**）。
- 根上静态值：`--skz-pulse-c: var(--skz-color)`、`--skz-shimmer-p: -60`（不写的话 @property 的 initial-value 是写死的 #d9dde3，深色主题下视口外的项会错色）。

同步方式选 WAAPI `startTime = 0`，同时做了对照：负 `animation-delay` 和不对齐（见第 5 节）。

## 5. 同步方式对照（probe-result.json，2000 卡片，慢速连续滚动 120 帧）

| 方式 | shimmer：p 极差>1 的帧数 | pulse：颜色极差>2 的帧数 | 静止（随机 10 次）极差 |
|---|---|---|---|
| WAAPI `startTime=0`（采用） | 0/120 | 0/120 | 0 |
| 负 `animation-delay = -(t mod 3000)` | 115/120 | 0/120 | 0 |
| 不对齐 | 115/120 | 13/120（最大 16 级） | 0（见注） |

- 注：静止 10 次里"不对齐"极差也是 0，是因为滚动后等了 700ms，视口内所有卡片都是同一时刻（≈同一帧）进入、起点相同，没有新旧并存，**这一项没有区分度**，真正区分要看"滚动中新旧并存"那一列。
- delay 方案的问题：起点是 IO 回调那一刻算的，实际动画起点落在下一帧，各卡片偏差不同（pulse 颜色变化慢所以看不出，shimmer 的高光位置会各差一帧）；而且要写每个项的内联 style。周期必须用 2×duration（pulse 是 alternate，用 1×duration 取模会让奇偶周期的卡片方向相反，这是 antigravity 原型里的一个 bug）。
- **这一组数据的幅度不可信**：probe 里 shimmer 的帧间隔被我探针自己每帧的强制样式/布局读取撑到了约 200ms（pulse 没有；只用 rAF 计时的 probe2 里是 16.7ms），delay 方案一帧的偏差因此被放大。结论方向（WAAPI 精确、delay 差一帧、不对齐会错位）成立，delay 的具体差值没有记录。
- 早先 verify 里"滚动后第 1 帧 p 与理论相位差 16~24"同源：是探针读到上一帧的值（帧间隔约 200ms），不是同步失败（各卡片之间极差始终为 0）。

## 7. antigravity 做了什么

调用后 5 分钟超时，返回的只有 "print timeout"，没有结论、没有数据。它留下的东西：`a.css`、`perf-a.js`、`perf.html`、`scenarios.json`、`run-verify.mjs`、`verify.mjs`（`results.jsonl`、`verify.log` 都是空文件），以及一个无主的 `bench/kit/bench.lock`（owner 的 pid 43320 已不存在，我确认后删掉了）。我读完判断不能用，全部删除重写：
- 它的 `perf.html` 没 import `variants/global.ts`，"现行"组实际没有防火墙；
- 负 delay 用 `now % 1500` 而不是 `% 3000`，pulse（alternate）会奇偶周期反向；
- 根上没给静态 `--skz-pulse-c`，视口外项会掉到 @property 的写死初值（深色主题错色）；
- 没有 MutationObserver / release 清理 / 动态插入处理。
它的任何数字都没有采用。

## 8. 结论与风险

**结论**
- 方案 A 机制成立：每帧样式重算在 2000 卡片下从现行 4~6ms 降到约 0.7~1.2ms，且基本不随列表总长度变（成本跟着可见项走）；同步可靠（WAAPI `startTime=0`，可见卡片之间相位恒等，且等于按时间轴算出的理论相位）；深浅色、动态插入、effect 切换、release 都通过。
- 但**收益只体现在每帧主线程余量上**：这台机器上 2000 卡片静止/滚动两边都是 60fps。只有在 CPU 4×/6× 降速下静止帧率才拉开（shimmer 35→60、12→约 42）。滚动下没有可靠差别。
- Paint 在 A 里略高，抵掉一部分样式收益（合计 2000 shimmer 中间只省 1.6ms，顶部省 4.8ms）。
- 现行防火墙的残余成本 ∝ 卡片总数（>2000 卡片/超长列表才会成为问题），A 把它变成 ∝ 可见数。

**实现复杂度**：原型 `scheme-a.js` 87 行（去掉注释和空行 68 行，其中约 25 行是开销统计和对照开关；去掉后核心约 40 行），CSS 约 25 行追加规则。比防火墙（`firewall.ts` 约 75 行）略多：多了 MutationObserver 和第二遍 `getAnimations`。

**风险 / 未覆盖**
1. 只在 Chrome（Windows）测，**Safari / Firefox 没测**；`CSSAnimation.startTime` 写入、`@property` 动画在项而非根上的行为，别的引擎没验证。
2. 不监听就不动：和防火墙相反，防火墙漏掉的新项还会照常动（只是没省开销），A 漏掉的项是**完全静止**。所以动态插入必须有 MutationObserver；列表容器本身被替换（框架重渲染换了 box）时我没处理，需要和 `enable()` 重调配合。
3. 列表项之外的零散骨头（根下非列表项部分）：按 CSS 规则它们会变成**静态**（根不动了，也没有项级动画），原型没做小范围动画，也**没实测**这种页面。有这种骨头的页面要么给它们补一个自己的动画，要么这类页面不走 A（找不到列表项时本来就回退根驱动）。
4. JS 计时器模式（`fps` 选项）与 A 的关系没处理（计时器写根上的内联变量，A 根上不动、项上有自己的动画，会各行其是）；现行也是"防火墙优先、计时器让路"，A 需要同样处理，没测。
5. 可见项很多的页面（大量很小的列表项同时在视口内，如网格/表格行）A 的优势会缩小，成本是 ∝ 可见元素数，没有这类场景的数据。
6. 大跳转后新进入的卡片有 1~2 帧静态，和防火墙一样，A 没改善。
7. 样本小：基准每格 3 次 trace 取中位，降速/滚动测试每格 3 次，噪声大的项（降速滚动、A-pulse 6× 离群值）已标注。

**建议**：值得转正吗——**有条件地值得，但不急**。
- 如果目标是"长列表（≥2000 卡片）在低端设备上保持流畅"，A 比现行防火墙更对症（降速 4×/6× 静止帧率差距明显）；机制简单、同步可靠、边界情况基本都能用现成手段覆盖。
- 如果目标场景是桌面端、几百到两千卡片，现行防火墙已经 60fps，A 多换来的是 ~4ms 余量，同时多出"漏项就静止"这一类新风险，和 Paint 略增。性价比一般。
- 转正前至少要补：Safari/Firefox 验证、零散骨头策略、与计时器模式的共存、容器替换处理。折中办法：把 A 做成 `engine` 或 `enable` 的可选项（如 `visibleOnly: true`），默认仍用防火墙。
