# sweep 光带"根太高就看不见"：根因、修复、数据

日期 2026-10-09。环境同矩阵报告：i5-13500 + Intel UHD 770（集显）、Chrome 154、视口 1200x800、DPR 1、独立 Chrome（端口 9477、临时 user-data-dir）。
基准页 `perf.html` 是矩阵 `perf.html` 的拷贝，只加了两件事：sweep CSS 取自本目录 `sweep-<v>.css`（`orig` = 修复前，`new` = 修复后，都由 `src/styles/entries/sweep.scss` 用 sass 编出），以及 `theme=dark` 参数。全部走真实 `enable()`。

## 1. 根因：不是 GPU 纹理上限，是 `skewX` 绕根中心倾斜

光带伪元素的 `transform` 是 `translateX(...) skewX(-12deg)`，`transform-origin` 默认在伪元素中心。skewX 让光带上每一行的水平偏移 = `(y - 中心y) * tan(12°)`。根高 H 时，根顶部那一行的偏移是 `0.106 * H`：H = 40k 时约 4260px，整条光带在根顶部被斜到视口右边几千像素之外；只有根纵向正中间那一段光带才落在视口里。合成层本身一直存在、一直在画。

判定可见的粗略条件（根宽 W，在根顶部看）：H < 约 15.7 * W。W = 1185 时是 18.6k px，和矩阵报告的"18940 勉强可见、20293 消失"吻合；根更窄阈值更小（375px 宽的手机根只有约 5.9k px）。

### 证据（逐项实验）

| 假设 | 实验 | 结果 | 结论 |
| ---- | ---- | ---- | ---- |
| 合成层超过纹理上限被丢 | `exp4-layers`：CDP `LayerTree` 读 40049px 根的层 | 存在 1185x40081、`drawsContent: true` 的层，DPR 1 / 2 都在；层的变换矩阵带 skew（m21 = -0.21）且 x 平移 3297~3338px | 排除：层没丢，是被斜到屏幕外 |
| 高度 x DPR 超限 | `exp2-cause` DPR=2、40k 根，滚到根中部 | 中部可见（12.6 万个像素变化），顶部不可见 | 排除 |
| `will-change: transform` | 去掉 will-change，40k 根 | 现象不变：滚到 50% 可见，0/25/75/100% 不可见 | 排除 |
| `mix-blend-mode` 隔离 | 40k 根改 `mix-blend-mode: normal` | 现象不变，只在 50% 可见 | 排除 |
| **skewX** | 40k 根，同样的动画改成只平移（去掉 skew） | **滚动 0/25/50/75/100% 五个位置全部可见**，光带横向范围固定 460~867px | **确认** |
| skew 的原点 | 40k 根，`transform-origin: 50% 0` | 变成只有滚到顶部（0%）可见，其余位置不可见 | 确认几何：可见位置随原点走 |

`exp2-cause` 的结果见 `results/exp2-cause.jsonl`，实验里"可见"= 暂停在 t=0 与 t=550ms 两张整视口截图的像素差 > 0（`diff` 解 PNG 逐像素比）。**旧的 md5 判断有坑**：t=700ms 时光带本来就出了右边界，会误判成不可见，所以改用 t=0（光带在左侧屏外）对 t=250/550ms。

## 2. 修复（只改了 `src/styles/` 下的两个文件）

`src/styles/_sweep-mixin.scss`：
- 关键帧和伪元素初值里的 `skewX(-12deg)` 改成 `skewX(var(--skz-sweep-skew))`，`--skz-sweep-skew` 默认 `0deg`（光带竖直，高度无关）。
- 想要旧的 12° 斜光带，在根上设 `--skz-sweep-skew: -12deg`。旧行为保留给短根（见下文：在 5 张卡的根上，`orig` 与 `new + skew:-12deg` 的像素差统计逐项完全一致）。注释里写了"超过约 16 倍根宽会看不见"的警告。

`src/styles/_sweep.scss`：顶部注释补一句。`entries/sweep.scss` 没动。两种模式共用同一份规则，所以 `skz-sweep="bg"` 同步修复；`_legacy-fallback.scss`（老浏览器降级到 sweep）也复用 `sk-sweep`，一并修复。

**试过但放弃的方案**：
- 把斜度做进分段（`repeat-y` 的 64px 小块里画 102deg 渐变）：斜度每 64px 复位一次，宏观上还是竖直光带，还多了锯齿，纯属白折腾。
- `position: sticky` 的视口高度光带：根是 flex / grid 时伪元素会变成 flex 项，破坏布局；`position: fixed` 需要 `clip-path` 才能裁到根里，而 `clip-path` 会让根变成独立图层，破坏 `mix-blend-mode`（源码注释里已有此结论）。没做实验，只是依据已有注释放弃。
- 想保留 12° 斜度又任意高度都可见，在"单根单伪元素、纯 CSS"的约束下做不到：任何跨全高的直线斜纹，水平漂移都正比于高度。

短根的 A/B（两边光带都可见，`perf4` 交错 3 轮，混合模式）：

| 根 | 修复前 GPU / 合成器 ms | 修复后 GPU / 合成器 ms | fps |
| -- | ---------------------- | ---------------------- | --- |
| 37 张（5k px） | 1.5~1.8 / 1.4~1.6 | 2.0~2.1 / 1.8~2.1 | 全部 60.4 |

结论：**帧率不变（60.4），主线程多约 0.05~0.2ms 样式重算；GPU / 合成器每帧多约 0.5~2ms，这是"光带真的在画"的代价**（修复前那几格 GPU 接近 0，是因为什么都没画出来）。已知异常：`new` 在 n=37 上 5 次独立运行里有 2 次出现 GPU 19~40ms / fps 37~49（perf2、perf3 各一次），重复 3 轮交错（perf4）全部正常；`orig` 没出现过。没查到原因（疑似整机 GPU 被别的程序占用，或首次合成混合模式时的一次性开销），**没验证**，所以不能保证偶发抖动与修复无关。

PrePaint 在 2000 张混合模式 4.77 -> 6.20 ms 的差异未做反向复测，批间噪声也可能有 1ms 以上，不要当真。

### 3.3 两种模式视觉对比（`exp3-visual`，5 张卡的短根，暂停在 t=550ms，与 t=0 逐像素比；按 t=0 时像素的原色分类）

`变化像素数 / 平均变化量(0~255)`。骨头 = 要被提亮的目标；卡片底、页面底 = 不该被碰的容器（漏光）。

| 主题 | 模式 | 骨头 | 卡片底 | 页面底 | 其它（文字 / 边框） |
| ---- | ---- | ---- | ------ | ------ | ------------------- |
| 浅 | 混合（lighten） | 21946 / 7.6 | **0 / 0** | **0 / 0** | 4078 / 8.1 |
| 浅 | bg | 22076 / 10.0 | 216726 / 1.9 | 4433 / 1.0 | 4157 / 8.6 |
| 深 | 混合（soft-light） | 22082 / 11.0 | **242671 / 9.9** | **14054 / 7.5** | 3896 / 3.1 |
| 深 | bg | 22226 / 8.0 | 104929 / 1.0 | 6562 / 4.8 | 4247 / 51.5 |

- 浅色：混合模式零漏光，是最干净的；bg 模式会把整块白卡片轻微拉向容器色（平均 1.9 级，肉眼几乎看不出）。
- 深色：混合模式（soft-light）几乎等于"整片提亮"：卡片底变化量 9.9，和骨头的 11.0 差不多，另外光带上下各 16px 的 bleed 还会漏到根外的页面背景；bg 模式只有 1.0，干净得多，但光带在深色下是把骨头"压暗"到容器色，对比度低，需要用户给 `--skz-sweep-bg-rgb`（取根里最亮的容器色）。
- bg 模式的"其它"在深色下 51.5：我的页面里文字是默认黑色，被拉向容器色（暗）的幅度大；真实深色页面里文字是浅色，拉向深色容器同样会变暗，符合源码里写的"比 x 更亮 / 更暗的内容会被拉向 x"的副作用。
- `new + skew:-12deg`（短根）与 `orig` 的统计数字逐项完全相同，说明旧的斜光带可以无损保留。

截图：`shots/vis-<light|dark>-<blend|bg>-<orig|new|newskew>-t550.png`；放大 16 倍的差异图 `shots/visdiff-*.png`（黑底，白色 = 被光带改变的像素，可看光带形状）。

### 3.4 功能抽查（`exp6-functional`，`demo/.tmp-sweep/multi.html`：3 个根并存）

- 3 个根各自独立：A（混合）、C（bg）有 `skz-sweep` 动画在 running；B（`skz-paused`）`animation-name: none`，光带像素差为 0，懒渲染暂停仍然有效。
- A 里的 `skz-ignore` 按钮仍可交互（`pointer-events: auto`），但仍会被光带扫到（像素差 max 122，源码注释已声明，行为未变）。
- 滚出视口再滚回，动画仍在（实验里手动暂停所以显示 paused，`getAnimations()` 里仍有 1 个 `skz-sweep`）。
- `vp test run test/styles.test.ts`：14 / 14 通过。没有新增单测（只允许改 `src/styles` 下的指定文件和临时目录，`test/` 不在范围内）。

## 4. 没验证 / 已知限制

- `dist/sweep.css` 没重新构建（`pnpm build` 会动共享的 dist，不在我的文件边界内）；基准页用的是 sass 直接编出的 `sweep-new.css`，与 build 产物只差压缩和前缀，没有逐字节比对。
- 只测了 Chrome 154 / Windows / Intel 集显；Safari、Firefox、独显、手机没测。`skewX(var())` 在关键帧里使用，Chrome 里仍是合成器动画（`getAnimations` + LayerTree 确认），其它浏览器未测。
- 竖直光带与旧的 12° 斜光带观感不同（默认变了）。没做真人 A/B 评审，只有像素统计。
- 没测 CPU 4x 降速、DPR 2 下的性能、多个相邻长根同时在屏的情况。
- n=37 上偶发的 GPU 抖动（见 3.2）原因不明。
- 旧的"光带可见"阈值公式（约 15.7 * 根宽）是几何推导 + 单点实测，没有扫不同宽度验证。
