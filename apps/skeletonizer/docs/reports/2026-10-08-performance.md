## TL;DR

- **第 6 节是空闲环境复测，以它为准**；第 1~3 节是 CPU 占满时测的，只看相对排序。
- 空闲复测：fade / solid 在 4000、16000 元素下都贴着 16.6ms；pulse 4000 元素约 64ms（约 15 帧/秒），16000 元素约 271ms；叶子 shimmer 最便宜，4000 元素约 26ms。
- 静态规则不贵：约 4000 个元素时，四档 CSS 加起来一次性约 70ms。
- **贵的是动画**：旧默认（每个元素各挂一个动画）4000 元素每帧 231ms，约 4 帧/秒。
- 优化后默认改成**根级 opacity 的 fade**：同样 4000 / 16000 个元素，每帧稳定 16.5ms，跟 `solid` 一样。
- `pulse` / `shimmer` 仍是元素级动画，**没变快**，当时靠 `enable()` 的阈值保护（超过 300 个元素自动降 fade），**该保护后来已移除**，是否使用由调用方决定。

环境：Windows 桌面 Chrome（DevTools 协议驱动），本机单次测量，**没有跨机器、跨浏览器**。

> ⚠️ **测量环境不干净**：事后查到本机 CPU 持续 100%（20 个逻辑核被占满，有 Rust 编译在跑），这些数字很可能是在 CPU 争抢下测的。**绝对数值不可信，尤其是主线程耗时（pulse / shimmer 每帧、开启耗时）；`fade` 和 `solid` 贴着 16.6ms 是被 vsync 封顶的，受影响小。** 各配置之间的相对排序大概率还成立，但倍数要等机器空闲时重测。第 4 节那个开启耗时异常，也不能排除是调度噪声。基准页 `demo/bench.html`，每张卡片约 8 个元素（img、h3、p、span、i、button 等）；控制台里可以直接 `await bench(500, [['sk-effect','pulse']])` 复现每帧耗时。

## 1. 优化前

### 1.1 开启骨架的一次性耗时（500 张卡片 ≈ 4000 元素，强制样式 + 布局）

| 加载的样式                          | 耗时      |
| ----------------------------------- | --------- |
| 无                                  | 0.1ms     |
| 兜底层                              | 29ms      |
| + 第 0 档                           | 58ms      |
| + 第 1 档                           | 66ms      |
| + 第 2 档（含 `:has`）              | 69ms      |
| + effects.css（旧版，含元素级动画） | **459ms** |

静态规则合计约 17µs/元素；`:has` 那条规则几乎没成本（但测试页里没有 `sk-ignore`，有的话没测）。动画一进来一次性耗时涨 6 倍，因为要给每个元素创建动画对象。

### 1.2 动画每帧耗时（目标 16.6ms）

| 配置                                         | 4000 元素 | 16000 元素 |
| -------------------------------------------- | --------- | ---------- |
| 旧默认（下划线文字 pulse，每个元素一个动画） | 231~241ms | 963ms      |
| pulse                                        | 268ms     | 942ms      |
| 叶子模式 shimmer                             | 99~115ms  | 458ms      |
| solid（无动画）                              | 16.6ms    | 16.5ms     |

结论：成本约 58µs/元素/帧，线性增长，主线程被占满。

### 1.3 当时试过的几个替代方案（4000 元素每帧）

| 方案                                                     | 耗时       | 评价                                                   |
| -------------------------------------------------------- | ---------- | ------------------------------------------------------ |
| A. 根上一个注册的 `@property` 颜色变量做动画，元素引用它 | 64ms       | 好 3.6 倍，但仍要每帧重算所有元素                      |
| C. 叶子 shimmer 同理，根上一个 `--sk-x`                  | 84ms       | 意义不大                                               |
| D. 去掉 `background-attachment: fixed`                   | 99ms       | **没变化**，说明瓶颈不在 fixed，而在每个元素各一个动画 |
| **B. 根整体 opacity 脉冲**                               | **16.6ms** | 和 solid 一样，动画跑在合成器线程                      |

## 2. 已落地的三条优化

1. **默认效果改成根级 `opacity` 脉冲（`fade`）**。没写 `sk-effect` 时生效；根里含 `sk-ignore` 时，隐式默认不开 fade（`:has([sk-ignore])` 判断，否则会把 ignore 的内容一起淡掉），要强制开就显式写 `sk-effect="fade"`。`prefers-reduced-motion` 下关闭。
2. **去掉 `*` 上的 `animation`**。第 1 档不再给所有元素挂动画，元素级动画只在显式选 `pulse` / `shimmer` 时才通过 `effects.css` 里的限定选择器生效。
3. **`enable()` 加阈值保护（后已移除，见第 6 节末）**。选了 `pulse` / `shimmer` 且根下元素数超过 `maxAnimated`（默认 `MAX_ANIMATED = 300`）时，自动改写成 `fade`；传大数可以强制保留。只管通过 `enable()` / `<sk-skeleton>` 进来的；纯 HTML 里直接写 `sk-effect="shimmer"` 不受保护。

## 3. 优化后复测

| 配置                           | 4000 元素每帧 | 16000 元素每帧 |
| ------------------------------ | ------------- | -------------- |
| 页面无骨架（对照，有测量噪声） | 18.3ms        | 22.1ms         |
| **默认（fade）**               | **16.5ms**    | **16.8ms**     |
| solid                          | 16.7ms        | 16.7ms         |
| pulse（元素级，下划线文字）    | 255ms         | 896ms          |
| shimmer（元素级，叶子模式）    | 99.6ms        | 452ms          |

`enable(root, { effect: 'shimmer' })` 在 4000 / 16000 个元素的根上都被改写成 `fade`；传 `maxAnimated: 1e9` 则保留 `shimmer`，都已验证。

默认路径的一次性开启耗时：4000 元素约 83ms（优化前 369ms）。

## 4. 没量清楚的地方（别当结论用）

- **开启耗时的一个异常**：16000 元素下，默认（fade）强制布局只要 0.5~1.4ms，等同配置换成 `sk-effect="solid"` 却要 175ms；改成"等到下一帧"的口径后，默认约 6~18ms、solid 约 250~290ms，差距仍在。**我没找到原因**，不能据此说默认路径更快，只能说"每帧耗时"这个指标是可信的。需要 Performance trace 才能定位。
- **滚动性能没测**：`background-attachment: fixed` 是否拖慢滚动，没验证（D 方案只证明它不是动画开销的瓶颈）。
- `pulse` / `shimmer` 在元素级仍然很贵，目前没有自动兜底（阈值保护已移除）；下面几条没做：根上叠 `::after` 渐变条用 `transform` 做 shimmer（会提亮整个根，未验证）、屏幕外根用 `IntersectionObserver` 暂停动画。
- 只测了桌面 Chrome；手机和低端机会更差，估计倍数不可靠。

## 5. sweep 原型：整个根一个 `::after` 扫光（只看了视觉，性能未测）

`sk-effect="sweep"`：根上一个 `::after` 渐变条，`transform` 平移（合成器线程），`mix-blend-mode: soft-light` 让它主要提亮中灰的骨头。根会被加上 `position: relative` 和裁剪（`overflow: clip`）。

视觉观察（桌面 Chrome，动画冻结在中段后截图）：

| 浅色                           | 深色                          |
| ------------------------------ | ----------------------------- |
| ![](../assets/sweep-light.png) | ![](../assets/sweep-dark.png) |

- ✅ **浅色下基本符合预期**：灰骨头被提亮，近白的卡片背景几乎看不出变化。
- ⚠️ **深色下会漏到容器背景**：卡片背景是中间调，也被提亮成一道浅色竖条。把深色高光从 .6 降到 .22 后明显淡了，但没消失。这是混合模式的固有局限，不是调参能彻底解决的。
- ⚠️ **每个根各扫各的**：一个根一个伪元素，多个根之间不同步（旧的 `fixed` 背景流光是全页同步的）。
- **边缘能看出边界，是三个原因叠在一起**（先用调试轮廓定位，再用截图像素逐行验证）：
  1. **【主因】渐变角度**：最初用 `linear-gradient(100deg, …)`，伪元素盒子 180×340，倾斜渐变线长约 236px，水平方向的一行只覆盖其中 12.5%~87.5%，**盒子边缘处透明度根本没降到 0**，被硬截断。像素实测：深色下同一行左端 41→54 平滑爬升，右端却从 46 一步掉回 41（断崖 5 个灰阶），所以又锐又不对称。改成水平 `90deg`，倾斜观感改用 `skewX(-12deg)`；复测同一批行，**相邻像素最大落差 = 1 个灰阶**，只剩 8 位色深的正常条带。
  2. **马赫带**：纯线性三角形轮廓在端点斜率突变，肉眼会把拐点看成一条边。改成 smoothstep 钟形（11 个色标）。
  3. **上下硬边（以及我第一次修它时引入的空白）**：demo 里根是卡片里面的内层 div（根盒子 451×340，外层卡片 978×413），伪元素被裁在根盒子里，高光在上下边缘戛然而止。第一版修法是整根伪元素做竖向淡出（上下各 15%），结果光带上下各空出一截，**用户反馈"光带要铺满甚至超出容器"**。现在改成：伪元素上下各多出 `--sk-sweep-bleed`（默认 16px），淡出只发生在多出来的这一截，根的盒子内全程满强度；根用 `clip-path: inset(-50vh 0)` 只裁左右、放开上下（不用 `overflow`，免得变成滚动容器）。像素实测（深色，竖向取列）：根顶上方 16px 起亮度从 41 爬升，**到根顶边正好达到满强度**，根底下方约 18px 才落回 41。盒子内部亮度随高度缓慢下降是 `skewX` 让光带随行水平偏移造成的，不是空白。
  - 另外：渐变两端写 `rgba(255,255,255,0)` 而不是 `transparent`，避免黑色透明参与插值时发暗。
  - 教训：前两轮我只凭肉眼和"透明度写了 0"就下结论，没量像素，所以先后修了两个次要原因才碰到主因。
- ❓ **性能没测**：测量时本机 CPU 仍被占满，等空闲后再和 fade / pulse / shimmer 一起复测。
- ❓ 根的 `::after` 被业务样式占用、根内绝对定位后代的参照物被改成根，这两个风险只是推断，没在真实页面里验证。

## 6. 空闲环境复测（2026-10-08）

环境：Windows 桌面，i5-13500，Chrome 154（独立用户目录，前台窗口，DevTools 协议驱动），基准页 `demo/bench.html` 的 `bench()`。每种配置 3 次、每次采样 2 秒，取中位数。同一配置 3 次之间差距基本在 10% 以内，数据可信；CPU 采样没取到数值，只能从结果稳定性判断环境干净。

| 配置              | 4000 元素每帧 | 16000 元素每帧 |
| ----------------- | ------------- | -------------- |
| 无骨架（对照）    | 16.5ms        | 16.5ms         |
| **fade（默认）**  | **16.6ms**    | **16.6ms**     |
| solid             | 16.6ms        | 16.6ms         |
| sweep ¹           | 16.6ms        | 16.6ms         |
| pulse（下划线）   | 63.5ms        | 271ms          |
| shimmer（下划线） | 75.2ms        | 276ms          |
| pulse（叶子）     | 54.3ms        | 195ms          |
| shimmer（叶子）   | 26.3ms        | 88.7ms         |

¹ sweep 的平移动画目前在 `effects.scss` 里是注释掉的，这里测的是静态扫光条，不代表动画开启后的成本。

结论：

- 比第 3 节（CPU 占满时）快了约 2~5 倍，**第 3 节的绝对数值作废**，相对排序没变。
- fade / solid 无论元素多少都被 vsync 封顶在 16.6ms，默认路径没有性能问题。
- 元素级动画成本仍随元素数线性增长：下划线 pulse 约 16µs/元素/帧，叶子 shimmer 约 6µs/元素/帧。按 16.6ms 一帧推算，pulse 大约 1000 个元素就开始掉帧；原先的默认阈值 300 留有余量，叶子 shimmer 的余量更大。
- 第一次复测时启动 Chrome 的 CPU 峰值未平复，重型动画 3 次之间差了 2 倍，已丢弃，只用第二次的数据。
- **自动降级已移除**：库不再根据元素数把 `pulse` / `shimmer` 降成 `fade`，也不再有 `maxAnimated` 选项；上面的数据留给使用者自己判断。

### 6.1 shimmer 降帧（`--x-ske-shimmer-timing: steps(n)`）复测

叶子模式 shimmer，三种写法交替跑 5 轮取中位数（每帧耗时，ms）。测试时本机仍有 rustc 在后台编译，CPU 约 13%~33%，误差偏大。

| 写法                | 4000 元素 | 16000 元素 |
| ------------------- | --------- | ---------- |
| linear（默认）      | 21.0      | 80.2       |
| steps(45)，约 30fps | 19.1      | 83.0       |
| steps(36)，约 24fps | 17.1      | 83.0       |

- 4000 元素：24fps 比 linear 低约 4ms，已经贴近 16.6ms 的 vsync 下限，但 linear 本身就只有 21ms，绝对收益小。
- 16000 元素：三种写法没有差别。降低样式变化的频率没有降低每帧耗时，原因没有查清，只能说 `steps()` 对大骨架没用。

## 7. 原型：根驱动动画 + content-visibility（2026-10-08）

### 7.1 先发现的问题：元素级 pulse 和下划线模式的动画看不见

骨头的 `background-color` 和下划线的 `text-decoration-color` 都写了 `!important`，按层叠规则它们压过动画，所以元素级 `pulse` 的颜色根本不变；下划线模式下 `[x-ske-effect]` 的 `*` 规则又把媒体骨头的 shimmer 动画换成了下划线颜色动画。隔 700ms 取两次计算样式：

| 模式                  | 图片骨头     | h3 文字        |
| --------------------- | ------------ | -------------- |
| pulse 旧（元素级）    | 颜色静止     | 下划线颜色静止 |
| shimmer 下划线 旧     | 流光位置静止 | 下划线颜色静止 |
| shimmer 叶子 旧       | 流光在动     | 流光在动       |
| pulse 根驱动          | 颜色在变     | 下划线颜色在变 |
| shimmer 下划线 根驱动 | 流光在动     | 下划线颜色在变 |
| shimmer 叶子 根驱动   | 流光在动     | 流光在动       |

也就是说，之前各节里"pulse 每帧 200 多 ms"测的是一个**看不出效果、只花钱**的动画。

### 7.2 每帧耗时（ms，3 轮交替取中位数）

做法：`@property` 注册 `--x-ske-shimmer-p`（流光位置）和 `--x-ske-pulse-c`（脉冲颜色），只在根上跑一个动画，骨头只读继承下来的变量。`x-ske-cv` 给根的直接子元素加 `content-visibility: auto`。测试时后台仍有 rustc 进程，CPU 约 9%~17%，个别轮次有尖峰，取中位数。

| 配置                     | 4000 元素 | 16000 元素 |
| ------------------------ | --------- | ---------- |
| pulse 下划线 旧          | 83.4      | 286.5      |
| pulse 下划线 根驱动      | 17.6      | 56.6       |
| pulse 下划线 根驱动 + cv | 16.7      | 16.6       |
| shimmer 下划线 旧        | 72.0      | 277.6      |
| shimmer 下划线 根驱动    | 17.6      | 57.6       |
| shimmer 叶子 旧          | 26.0      | 80.8       |
| shimmer 叶子 根驱动      | 17.7      | 59.0       |
| shimmer 叶子 根驱动 + cv | 16.6      | 21.6       |

- 根驱动：下划线模式快约 5 倍，而且动画终于看得见；叶子 shimmer 快约 1.4 倍（每帧仍要重绘所有骨头，省掉的只是动画调度）。4000 元素下已经贴着 vsync。
- content-visibility：基准页 16000 元素绝大部分在视口外，所以收益接近"只渲染可见部分"，16000 元素也回到 vsync 附近。满屏都可见时它没有收益。
- 未验证：Safari / Firefox 上的表现；`content-visibility` 裁掉溢出内容、估高不准导致滚动跳动的实际影响。

### 7.3 转正

根驱动已转正，元素级写法删除（备份在 `archive/2026-10-08-element-anim/`）。转正后复测（后台 rustc 编译，CPU 约 24%~39%，噪声偏大）与 7.2 一致：pulse / shimmer 下划线 4000 元素约 17.4ms、16000 元素约 66ms，叶子 shimmer + `x-ske-cv` 16000 元素约 30ms。

降级路径验证：把构建产物里的 `@supports (color: rgb(from red r g b))` 改成必然不成立的条件，模拟不支持 `@property` 的浏览器：pulse / shimmer 的根动画都变成 `x-ske-fade`，骨头无渐变背景、颜色静止；根里有 `x-ske-ignore` 时根动画为 `none`。支持路径下 pulse 颜色、shimmer 流光位置、下划线颜色都在变。只在 Chrome 里模拟，真实的老版本浏览器没测。

### 7.4 根标记 class 与属性的 A/B 对比

把根标记从 `.x-ske` 换成 `[x-ske]`（去掉补回 class 的 MutationObserver）前做的对比。两份 CSS 由同一份 scss 编出，交替测 5 轮取中位数；当时后台有 rustc 编译，噪声偏大。

| 测量项                 | class | 属性  | 差异                   |
| ---------------------- | ----- | ----- | ---------------------- |
| 开启 4000 元素 默认    | 21.5  | 21.3  | -0.9%                  |
| 开启 16000 元素 默认   | 136.2 | 170.1 | +24.9%（5 轮范围重叠） |
| 开启 16000 元素 叶子   | 152.1 | 161.3 | +6.0%                  |
| 每帧 16000 fade        | 16.5  | 16.6  | +0.6%                  |
| 每帧 4000 pulse        | 70.2  | 66.2  | -5.7%                  |
| 每帧 4000 shimmer 叶子 | 26.2  | 25.1  | -4.2%                  |

结论：动画每帧无差别；16000 元素开启耗时可能有 0~25% 额外开销，未定论。脚本与说明见 `bench/2026-10-08/`。

## 8. 深入分析：每帧耗时拆分与优化（CPU 空闲，2026-10-08）

### 8.1 方法

- 环境：i5-13500 + Intel UHD 770，Chrome 154 独立用户目录、前台窗口；测试期间 CPU 10%~18%，无编译任务。
- 页面同基准页（每张卡片约 8 个元素），CSS 用 `sass` 直接编译、按实验需要改写成变体。
- 每个场景预热 0.8 秒，录 3 次 2.5 秒 Chrome trace，按线程和事件类型拆分，除以帧数得到每帧耗时，取中位数。
  主线程看 `UpdateLayoutTree`（样式重算）、`Layout`、`PrePaint`、`Paint`。
- 开启耗时：切换根上的 `x-ske` 后强制样式 + 布局，取 15 次中位数。

### 8.2 基线：时间花在哪

| 场景（16000 元素） | 帧率 | 样式重算 | PrePaint | 绘制 |
| ------------------ | ---- | -------- | -------- | ---- |
| fade               | 60   | 0.23     | 0.02     | 0    |
| sweep              | 60   | 1.12     | 7.16     | 0    |
| pulse 下划线       | 22   | 40.2     | 3.17     | 1.72 |
| shimmer 下划线     | 21   | 41.7     | 3.56     | 2.00 |
| shimmer 叶子       | 19   | 47.2     | 3.57     | 2.40 |
| shimmer 叶子 + cv  | 55   | 9.6      | 1.58     | 1.33 |

结论：pulse / shimmer 的瓶颈是**样式重算**，绘制只占零头。根上被动画的变量会继承，所以每帧根下所有元素都要重算样式，重算时所有选择器都要重新匹配一遍。

### 8.3 实验

| 实验                                                        | 结果（16000 元素）                                                              | 结论                                                        |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 根动画加 `steps(36)` / `steps(18)`                          | 样式重算 46.5 → 52.3 / 47.6                                                     | 没用：Chrome 每帧都推进根动画并让子树重算，降帧只省一点绘制 |
| 去掉第 2 档整档                                             | pulse 叶子 44.2 → 24.0；开启 151 → 62                                           | 第 2 档的 `:has` 规则是主要成本                             |
| 去掉第 1 档                                                 | pulse 下划线 40.5 → 32.2                                                        | 下划线规则约 8ms，是下划线模式的必要成本                    |
| 逐条去掉第 2 档规则                                         | `*:has([x-ske-ignore])` 约 10ms（下划线）；叶子骨头规则约 9ms；图标规则约 2~6ms | 前两条值得改                                                |
| `*:has([x-ske-ignore])` 前加根属性门控                      | 41.2 → 30.6，等同于删掉                                                         | 祖先属性能让浏览器快速跳过整条规则                          |
| 叶子规则 `:has(*)` → `:has(> *)`                            | 43.1 → 36.4                                                                     | 含义相同，只看直接子元素                                    |
| 隐式 fade 的 `:has([x-ske-ignore])`                         | 开启 144.5，显式 fade 66.8                                                      | 根上的 `:has` 让开启多出约 80ms                             |
| sweep 暂停光带动画                                          | PrePaint 5.6 → 0                                                                | sweep 的主线程开销来自光带动画本身                          |
| sweep 加 `contain: paint` / `isolation` / `contain: layout` | PrePaint 6.6~7.8，无改善                                                        | 挡不住；sweep 仍稳定 60 帧，不再处理                        |
| `x-ske-cv` 的开启耗时                                       | 225ms，不开约 70ms；4000 元素下 13.6 vs 16.9                                    | 子元素多时开启更贵，换来每帧大幅下降                        |

### 8.4 落地的优化与复测

1. 根里含忽略区时，`enable()` 在根上加 `x-ske-has-ignore`；下划线修正规则、隐式 fade 关闭规则、降级 fade 关闭规则都改为看这个属性，不再用 `:has([x-ske-ignore])`。纯 HTML 手写根时需要自己加。
2. 叶子骨头规则 `:not(:has(*))` 改成 `:not(:has(> *))`。

同一轮交替测量，优化前 → 优化后：

| 场景              | 4000 元素样式重算 | 16000 元素样式重算 | 16000 元素帧率 | 16000 元素开启 |
| ----------------- | ----------------- | ------------------ | -------------- | -------------- |
| 隐式 fade         | —                 | —                  | 60 → 60        | 139.5 → 63.5   |
| pulse 下划线      | 10.9 → 9.3        | 40.9 → 31.8        | 22 → 26        | 64.1 → 57.5    |
| shimmer 下划线    | 11.4 → 9.3        | 41.6 → 32.7        | 21 → 27        | 66.0 → 58.3    |
| shimmer 叶子      | 12.2 → 9.5        | 46.8 → 33.5        | 19 → 26        | 69.0 → 58.2    |
| shimmer 叶子 + cv | 4.1 → 2.9         | 11.1 → 7.7         | 60 → 60        | 228 → 222      |

忽略区行为复核：根上自动带 `x-ske-has-ignore`，隐式 fade 关闭，忽略区祖先不画下划线，忽略区按钮未被 inert、`pointer-events: auto`，关闭后根上无残留属性。

### 8.5 剩下的成本与没做的

- 优化后 16000 元素下 pulse / shimmer 每帧仍有约 32ms 样式重算，大头是"继承变量变化 → 全子树重算"本身，选择器已不是主要因素。想再降只能减少参与重算的元素：`x-ske-cv`（已有，可选）或拆成多个根。
- 图标启发式规则约 2~6ms，噪声较大，暂不动。
- sweep 光带动画每帧约 6ms PrePaint（16000 元素），原因在 Chrome 内部，仍稳定 60 帧。
- 只测了桌面 Chrome；Safari / Firefox 的选择器和 `:has` 实现不同，收益可能不一样。

## 9. 根驱动的成本来源与 SVG 方案（2026-10-08）

方法同第 8 节（CPU 空闲，trace 拆分，3 次中位数，叶子模式）。

### 9.1 根驱动还能怎么降

| 实验                                             | 4000 元素样式重算 | 16000 元素样式重算 | 结论                                                                                                       |
| ------------------------------------------------ | ----------------- | ------------------ | ---------------------------------------------------------------------------------------------------------- |
| 基线（CSS 动画驱动根变量）                       | 9.2               | 33.0               | —                                                                                                          |
| 根照常动画，但骨头不读变量                       | 8.9               | 32.6               | 成本几乎全在"继承变量变化 → 全子树重算"本身，跟谁读无关                                                    |
| 去掉第 1、2 档选择器                             | 6.8               | 24.1               | 选择器还占约 9ms（16000），已不是大头                                                                      |
| 改用标准属性 `color` 传色（骨头 `currentColor`） | 10.5              | 37.5               | 没用                                                                                                       |
| JS 每帧写根变量（pulse）                         | 4.6               | 16.8               | 便宜一半，原因是颜色取整后相邻帧常常不变、跳过写入；CSS 动画哪怕值没变也每帧触发重算（`steps()` 无效同理） |
| JS 每帧写根变量（shimmer）                       | 10.8              | 40.0               | 位置每帧都变，和 CSS 动画一样贵                                                                            |
| JS 限 30fps 写（pulse / shimmer）                | 3.0 / 5.3         | 15.5 / 39.3        | 中小规模能减半；16000 元素一帧本身超过 33ms，限速形同虚设                                                  |

结论：根驱动的单次更新成本约 2.3µs/元素，无法再从 CSS 侧压低；能降的只有"每秒更新几次"，需要 JS 计时器（已落地为 `fps` 选项，见 9.3）。大规模场景靠 `x-ske-cv` 或 SVG 方案。

### 9.2 SVG 方案

骨头背景用一张带 SMIL 动画的 SVG data URI（`background-attachment: fixed`，铺满视口，各骨头同步），根上不跑任何动画。截图确认画面在动、各骨头光带同步。正式构建复测：

| 场景                  | 4000 元素（帧率 / 样式 / PrePaint） | 16000 元素（帧率 / 样式 / PrePaint） | 16000 元素开启 |
| --------------------- | ----------------------------------- | ------------------------------------ | -------------- |
| shimmer 叶子 根驱动   | 60 / 10.1 / 1.2                     | 22 / 38.0 / 4.8                      | 66.9           |
| shimmer 叶子 SVG      | 60 / 0.07 / 3.7                     | 58 / 0.05 / 13.6                     | 71.0           |
| pulse 叶子 根驱动     | 60 / 8.9 / 0.5                      | 25.6 / 34.0 / 4.0                    | 69.4           |
| pulse 叶子 SVG        | 60 / 0.04 / 4.0                     | 58 / 0.03 / 13.3                     | 71.6           |
| shimmer 下划线 根驱动 | 60 / 10.3 / 0.9                     | 21.6 / 38.3 / 5.5                    | 86.1           |
| shimmer 下划线 SVG    | 60 / 0.07 / 1.6                     | 60 / 0.06 / 6.6                      | 85.6           |

- 样式重算归零；新增成本是 PrePaint（图片每帧变化要通知所有用到它的骨头），16000 元素约 13ms，仍在帧预算内。
- 不依赖 `@property`：在模拟"不支持"的构建里照样在动，`x-ske-fallback` 对它无效。
- 深色切换到深色图、`x-ske-paused` 去掉背景图，均已验证。
- 页面 SVG `<defs>` 里的渐变不能被 HTML 背景用 `url(#id)` 引用（只有 SVG 的 fill / stroke 可以，Firefox 另有 `element()`），所以用 data URI 图片而不是全局 defs。

### 9.3 JS 计时器（`fps` 选项）落地后复测

真实 `enable()`、正式构建 CSS，每帧样式重算 ms / 帧率：

| 场景                 | CSS 动画    | `fps: 30`   | `fps: 24`   |
| -------------------- | ----------- | ----------- | ----------- |
| pulse 叶子 4000      | 8.75 / 60   | 2.52 / 60   | 2.04 / 60   |
| shimmer 叶子 4000    | 9.74 / 60   | 4.74 / 60   | 3.13 / 60   |
| shimmer 下划线 4000  | 9.88 / 60   | 4.69 / 60   | —           |
| pulse 叶子 16000     | 33.3 / 26.8 | 14.9 / 37.6 | 11.5 / 44.8 |
| shimmer 叶子 16000   | 37.6 / 22   | 38.5 / 22   | 20.5 / 36.8 |
| shimmer 下划线 16000 | 35.1 / 23.6 | 35.3 / 23.6 | —           |

- pulse 收益来自两点：限速，加上颜色进度量化后相邻帧常常相同、直接跳过写入。
- 16000 元素下一帧本身超过 33ms，`fps: 30` 的间隔短于一帧，等于每帧都写，所以 shimmer 没收益；`fps: 24` 才能隔帧写。
- 浏览器内验证：根上无 CSS 动画、变量按帧率变化、深色主题下颜色跟随主题（`color-mix` 读主题变量）、截图确认画面在动、关闭后不留 `style` 属性。

## 10. 组合方案落地与复测（2026-10-09）

依据第 8、9 节和五个子代理实验（`bench/agents/`），落地四项：继承防火墙、SVG 运行时 blob、`fps: "auto"`、显式标记模式。正式构建 + 真实 `enable()`，3 次中位数（CPU 18%~40%，有其他进程）。

| 场景                                                | 4000 元素 帧率 / 样式重算 | 16000 元素 帧率 / 样式重算 / PrePaint |
| --------------------------------------------------- | ------------------------- | ------------------------------------- |
| 纯 CSS shimmer 叶子（无 JS，无防火墙）              | 57.6 / 12.7               | 16.8 / 49.4 / 7.1                     |
| `enable` shimmer 叶子（自动防火墙）                 | 60.4 / 1.7                | **60.4 / 6.1 / 0.3**                  |
| `enable` shimmer 叶子 SVG blob                      | 60.4 / 0.08               | 54 / 0.06 / 15.6                      |
| 纯 CSS pulse 下划线                                 | 59.2 / 12.3               | 18.4 / 46.6 / 4.7                     |
| `enable` pulse 下划线（自动防火墙）                 | 60.4 / 1.5                | **60.4 / 4.9 / 0.1**                  |
| 显式模式 纯 CSS shimmer                             | 59.6 / 12.2               | 18 / 46.8 / 6.5                       |
| 显式模式 `enable` shimmer（防火墙）                 | 60.4 / 1.6                | 60.4 / 5.9 / 0.2                      |
| 防火墙 + `fps: "auto"`（修复前）                    | 60.4 / 5.5                | 43.6 / 10.6                           |
| 防火墙 + `fps: "auto"`（钉住 `--x-ske-pulse-t` 后） | 60.4 / 6.2                | 38.8 / 14.1                           |
| 防火墙 + `fps: 24`（pulse 下划线）                  | 60.4 / 3.4                | 26.8 / 28.1                           |

结论：

- **继承防火墙是这一轮最大的收益**，默认路径 16000 元素回到 60 帧，比 SVG 方案还快，且颜色精确、无需配置。开启耗时 80ms 左右，与不开相近。
- **计时器与防火墙冲突**：计时器写根的内联变量，即使防火墙项上钉住了同名变量，子树仍被整体重算（推测是内联样式变更触发了子树重算，没查 Chromium 源码）。落地为互斥：找到列表项用防火墙，找不到才用计时器。
- **显式模式性能几乎没变**：实现是给推导规则加 `:not([x-ske-mode="explicit"])` 的根条件，浏览器仍要先匹配右侧元素再检查祖先，规则匹配成本省不掉；子代理测到的约 1/3 提升来自一份完全不含推导规则的样式表。显式模式按"控制"定位，不作为性能选项。
- **SVG blob**：浏览器内验证颜色与时长正确（根上改 `--x-ske-highlight: #ff0000` + `--x-ske-duration: 3s` 后 blob 内容为 `#ff0000`、`3000ms`，截图光带变红且各骨头同步；深色主题为 `#4b5563`）。
- **防火墙正确性**：200 张卡片时视口外 192 张带 `x-ske-fw`、视口内 0 张，滚到中间后重新分布；视口内骨头在动。显式模式下圆形头像保持 `50%` 圆角。

脚本、场景、原始结果与截图：`bench/2026-10-09-integration/`。

## 11. 基底 + 变体拆包后的复测（2026-10-09）

### 11.1 独立的 `explicit.css`

第 10 节里显式模式是给推导规则加 `:not([x-ske-mode="explicit"])` 的根条件，几乎没有提速。拆包后 `explicit.css` 是一份完全不含推导规则的样式表。带 `x-ske-bone` 标记的页面，叶子模式，3 次中位数（CSS 叠加 `global.css`）：

| 场景                                  | `base.css` 帧率 / 样式重算 | `explicit.css` 帧率 / 样式重算 |
| ------------------------------------- | -------------------------- | ------------------------------ |
| 4000 元素 纯 CSS shimmer              | 57 / 12.9                  | 60 / 7.4                       |
| 4000 元素 纯 CSS pulse                | 60 / 11.2                  | 60 / 7.0                       |
| 4000 元素 `enable` shimmer（防火墙）  | 60 / 1.9（开启 25ms）      | 60 / 1.2（开启 18ms）          |
| 16000 元素 纯 CSS shimmer             | 17 / 49.3                  | 24 / 31.9                      |
| 16000 元素 纯 CSS pulse               | 19 / 46.7                  | 31 / 26.1                      |
| 16000 元素 `enable` shimmer（防火墙） | 60 / 6.8（开启 80ms）      | 60 / 2.8（开启 61ms）          |

结论：不含推导规则后每个元素的重算更便宜，无防火墙时 -35%~44%，有防火墙时 -59%，开启快约 24%。

### 11.2 拆包时引入并修复的优先级问题

基底里 pulse / shimmer 退回 fade 的规则加了 `:not([x-ske-has-ignore])`，`:not()` 把括号里的属性也算进优先级，变成 (0,3,0)，压过变体的根驱动规则 (0,2,0)，结果加载了 `global.css` 也一直是 fade。第一次跑 11.1 的数据全部是 fade（样式重算约 0.2ms），据此发现。修复为 `:where(...)`（优先级 0），并验证 `base + global`、`explicit + global`、`global` 放在 `base` 之前三种顺序下根动画都是 `x-ske-shimmer-root, x-ske-pulse-root`；`test/styles.test.ts` 加了回归断言。
