# 2026-07-17-4: auto() 元素移除时主动清理,消除长跑内存渗漏

## 变更原因

评审现有"多 stage + 改 src"方案时提出隐患:`auto()` 长期持有被跟踪图片的 DOM 引用,是否会内存暴涨/泄漏、拖慢性能。

核查 `src/page/auto.ts` 后结论分两层:

- **已规避**:元素在 `tracked`(WeakRef)、`elUrl`/`elExpected`/`pendingFull`(WeakMap)里都是弱引用,元素本身能被 GC,不会因被跟踪而无法回收。
- **真实隐患**(缓慢渗漏,非暴涨):
  1. `tracked`/`stageOf`/`reconciled` 三个按 URL 的容器运行期只增不减(仅 `stop()` 才整体 clear),长跑 SPA + 海量不同图 URL 时元数据单调增长。
  2. `tracked` 的 Set 里死 WeakRef 空壳不移除,`swapAll`/`retryAll` 遍历成本随历史元素总数增长。
  3. MutationObserver 只处理 `addedNodes`,不处理 `removedNodes`——元素移除时不做任何清理。
  4. `IntersectionObserver`(`fullIO`)对未 `unobserve` 的已移除元素(尤其 `offViewport:'thumbnail'/'placeholder'` 模式下长期观察)存在观察记录残留,可能阻止 GC(实现相关,不保险)。

## 目的

把"元素离开 DOM"从"被动等 GC"改为"主动清理",消除元数据累积、死壳堆积与观察器残留。

## 落地方案

`src/page/auto.ts` 三处改动:

1. **新增 `untrackElement(el)`**:以 `el.isConnected` 守卫(排除"移除+重新插入"的移动场景,避免误清);`fullIO.unobserve(el)`、删 `pendingFull`/`elExpected`/`elUrl`;从该 URL 的 Set 删掉它的 WeakRef(并顺带清同集合里的死壳);Set 空则删 `tracked`/`stageOf`/`reconciled` 的该 URL 条目。
2. **新增 `untrackSubtree(node)`**:MutationObserver 的 `removedNodes` 只列子树根,故下钻 `querySelectorAll` 捕获嵌套的 `<img>`/背景元素,逐个 `untrackElement`。
3. **MutationObserver `childList` 分支**新增 `m.removedNodes.forEach(untrackSubtree)`。
4. **`swapAll`** 遍历时 `deref()===undefined` 的死壳顺手 `set.delete(ref)`,Set 空则回收该 URL 元数据。

`isConnected` 守卫是关键:MutationObserver 回调批量异步执行时 DOM 已是最终态,移动的元素 `isConnected` 为 true 不误清,真移除的为 false 才清理。

## 验证

- 新增测试 `test/auto.test.ts`「元素移出 DOM 后被清理,不再接收后续阶段」:track 后 `img.remove()`,再 emit `complete`;因测试仍持有 `img` 引用(WeakRef 可 deref),若未清理则会被 swap 到全图,断言 `src` 保持原值即证明已从 `tracked` 移除。与基线测试(在 DOM 内的元素确实会被 swap)形成对照,确保测试有区分力。
- `pnpm test` 109/109 通过;`pnpm build` 通过;`pnpm fmt` 净。

## 范围与后续

- 本次只治 `<img>`/背景元素的跟踪清理;`<video>` 走 `videoFacade`,其自身的移除清理不在本次范围。
- 未引入 `FinalizationRegistry` 兜底回收或 `tracked` 的 LRU 上限——按最小改动,当前"移除即清 + 遍历顺手清死壳"已覆盖主要渗漏路径,更激进的治理留待确有需要时再评估。
