# 2026-07-17-2: SW 注册时序的结论与接入姿势文档化

## 变更原因

使用方提出疑问:能否让 `registerImgprogressSW` 同步注册、省掉 `await`,以便首次访问的首屏 LCP 图也能被接管。围绕这个诉求做了一轮技术澄清,需要把结论沉淀成文档,避免后续重复讨论。

## 讨论结论

1. **同步注册做不到**:`navigator.serviceWorker.register()` 返回 Promise,SW 的 install/activate/claim 由事件循环驱动,本质异步;主线程忙等会阻止 SW 事件推进,造成死锁。没有"同步生效"这个状态。

2. **base64 内联 SW 脚本不可行**:浏览器要求 SW 脚本是同源 http(s) URL,拒绝 `data:` URL。且即便省掉脚本下载,install/activate/claim 的生命周期开销依然存在。

3. **首次访问的硬约束**:SW 管不到"当前这次访问里、在它就绪之前就发出的请求"。静态 HTML 里被 preload scanner 抢先请求的 `<img>` 必然漏拦。

4. **SPA 场景成立**:SPA 首屏图是应用入口执行后才渲染的,只要渲染前 `await` 到 SW 就绪即可接管。这点使用方判断正确。

5. **真正可用的优化 = 尽早注册**:在 `<head>` 内联一小段 `register()` 让 SW 下载/激活与应用包的下载/执行并行;bundle 内 `registerImgprogressSW` 因 register 幂等而复用,`await` 很快返回。应用包越大,并行收益越大。首次访问无缓存可命中,收益来自"提前并行"而非"利用缓存";`<link rel="preload">` 因 destination(serviceworker vs script)不匹配 + SW 脚本默认走 revalidation,不可靠,不推荐。

## 落地方案

**决定:不改代码,只在 README 补充接入姿势说明。**

评估过为"省掉 await"新增运行时兜底(SW 未就绪时先挂占位、就绪后接管),现状确认如下:

- `load()`(`src/page/load.ts`):SW 无 controller 时直接 emit complete 走原图,无等待。
- `auto()`(`src/page/auto.ts` 的 `track()`):不改元素 src,SW 未就绪时被跟踪的 `<img src>` 已由浏览器发起原图请求,追不上。
- 两者的缓存对账只补偿"错过的通知",解决不了首访 SW 未激活(缓存为空)。

结论是可靠的兜底只能落在显式模式(load / `<img-progress>`,src 由库控制),而 `auto()` 零改造与"抢在请求前挂占位"本质冲突。权衡后使用方选择暂不引入运行时兜底,仅以文档提示最佳实践。

**README 改动**:新增"让首屏也被接管:尽早注册 SW"一节,含 `<head>` 预注册 snippet、bundle 内 await 复用示例、SPA 场景说明与降级行为。

## 后续可选项(暂不做)

若日后需要"省掉 await 也能接管首屏",可在显式模式内新增 SW-ready 兜底:未就绪时先挂占位色块、await `navigator.serviceWorker.ready`(带超时降级)后再走渐进流程。`auto()` 若要支持,需业务方把首屏图改为 `<img data-src>` 半改造。
