## 6. 规格不清与保守取舍

1. **过渡垫片 `src/legacy-axios.d.ts`。** 要求删除旧文件对 axios 模块的扩展，但不许改的旧 `auth.ts`、`retry.ts` 还在读 `config.share`、`config.cache` 和 `AxiosRequestConfig['share']`，删掉扩展后 tsgo 会报 10 处错误（已实测，全在 `auth.ts`、`retry.ts`）。垫片只声明这两个字段，类型为 `unknown`，不含 mock。放在 `src/` 顶层而不是 `src/plugins/`，因为 `vite.config.ts` 的 pack 入口通配 `src/plugins/*.ts` 会匹配到 `.d.ts`。注意 `vp check --fix` 会把 `export {}` 当无用导出删掉，导致 `declare module` 变成覆盖整个 axios 类型的环境声明（tsgo 报 axios 没有 `create`），所以垫片用一个类型导出保持模块性。B3 重写 auth/retry 之后整份删除。
2. **share、cache 按请求开启。** 请求级写 `true`、策略名、数字或对象才开启；省略、`false`、`null`、`enable:false`、函数、数组等未声明值一律不开启。依据是 N6 与规格 §6.2、§6.3 的"开启：请求级…"，插件级没有"默认开启"字段。share 的非法策略字符串（如已删除的 `'none'`）按"开启，用插件级策略"处理，沿用旧的 `$resolvePolicy` 回退。
3. **share 首发的 patch 同时把 axios 层 `timeout` 置 0**（只在首发请求有正的超时时才加）。规格字面只写 `next({ signal: 共享 controller })`，但首发的 axios 超时会让共享请求在首发的截止时间失败并连累所有跟随者，与"单独离开只 reject 自己"自相矛盾，所以把超时完全交给各订阅者自己的计时器。代价是 `r.request.timeout` 显示为 0。订阅者超时的响应文案对齐 axios：`timeout of Nms exceeded`。
4. **共享表按策略分三张。** 旧实现一张表混放，同 key 的不同策略会读到字段不匹配的条目。
5. **end 的结果归属沿用旧行为。** 最新一次若被取消或失败，所有订阅者拿到该次结果；被顶替的调用若自己失败则丢弃。end 与 race 的订阅者提前离开不会中止各自的底层请求（它们用各自的 signal 与 axios 超时），只有 start 有共享 controller 可中止。
6. **到达 share 时逻辑信号已中止**（例如外层插件等待期间被取消）：直接 `cancel`，不创建条目、不触网。旧测试"已中止 signal 的单一订阅者：底层被 abort"改为"底层根本没发"。
7. **cache：`cache: true` 沿用插件级 `clone`、`expires`、`shouldCache`**，这是规格 §0 的"`true` 用插件级配置"。旧版 `true` 不带插件级 clone（只对象写法才带），属于行为变化，请发版时记进 CHANGELOG。
8. **cache clone 的范围。** 命中总是按策略拷贝；未命中返回时只对 `r.ok` 拷贝，失败响应不过用户的 clone 函数（否则网络错误的 `data` 是 `undefined`，自定义 clone 可能直接抛错，把本该返回的失败变成异常）。`'deep'` 在没有 `structuredClone` 时在发请求前抛错，不退化成浅拷贝。拷贝后的 R 用 `ctx.fail({ from, data })` 派生，所以自定义响应的扩展字段保留（有集成用例验证 `traceId`）。
9. **显式缓存键**（`cache: { key }`）不经过 key 服务，所以不含 `scope`，也优先于 `key: false`；空串和非字符串的键退回 key 服务。要做账号隔离请用 key 服务的 `scope`。
10. **屏障记录只在在途期间存在。** 请求结束时统一 `reclaim(key, false)`：没有在途请求时记录没有保留价值（之后发起的票据序号必然更大），所以不依赖 store 的淘汰通知，对任意第三方 store 都不会泄漏记录。规格 §6.3 写的是"条目被淘汰且没有在途请求时回收"，这是它的超集；R2-2（淘汰后在途旧响应不回写）仍成立，有用例。`cache-store.ts` 没改。
11. **注入 store 的边界。** 注入 `store` 后 `max` 不再生效；卸载只清空自己创建的内存 store，注入的由调用方管理；`extend()` 的子客户端会复用同一个注入对象（共享状态是调用方的选择）。`clear()` 返回物理条目数，含尚未惰性清理的过期条目。
12. **`removeCache`、`clearCache` 按插件名 `axp:cache` 经 `client.plugin` 取管理 API**，参数类型是 `Pick<AxpClient, 'plugin'>`，任何 R、任何 Schema 的客户端都能传。
13. **mock 的请求级对象不再认 `mock` 字段**（按终审裁决），关闭用 `false` 或 `enable:false`；`mock:{ mock:false }` 仍然会 mock。未声明的请求值（`0`、字符串、函数、`NaN`）按省略处理，由插件级 `mock` 决定。探测请求的 patch 只含改写后的地址加 `cache:false`、`share:false`，不动 key（地址变了，key 自然不同）。
14. **请求级回调的类型不是泛型。** `AxpRequestOptions` 是非泛型接口，所以请求级 `fallbackWhen`、`shouldCache` 的参数声明为 `IAxpResponse`；需要自定义 R 字段时请写在插件级回调（推断为 R），或自行收窄。这与 B2 的 loading、notify 处理一致。
15. **`unit/context.unit.test.ts` 里的 resolve 行改定位。** 清单把 `$resolveCache`、`$resolvePolicy`、`$resolveMock` 的行指向 `unit/context.unit.test.ts`，但解析统一走了 `resolveOption`，B2 同类行也是改定位；本批通过 rule、boundary 层的参数化表覆盖，没有为内部解析函数另写单测。
16. **未改内核，没有发现内核 bug。** 观察一处：B2 的 `uiClient` 参数类型是 `AxpPlugin<AxpResponse>[]`（`A` 固定为 void），带管理 API 的 cache 传不进去，所以新增了 `sourceClient`；`createTestClient` 本身没有这个限制。
