旧 bench/pipeline.bench.ts 未修改。新 bench（bench/client.bench.ts）沿用同样的薄内存 adapter、发送计数和独立信封；精简轮新增“0 / 3 / 8 个直通中间件”三个场景（自定义插件 `handle: (ctx, next) => next()`），并把 `URL` 常量改名为 `BENCH_URL`，避免遮蔽全局 URL。正式计时外自检：每个场景恰好触网一次、`inspect()` 层数等于预期、解包值正确。每场景预热 500ms、至少测 2000ms/100 样本。

**测量环境（决定了这些数字的可信度）。** 命令为 `vp test bench --run bench/client.bench.ts --outputJson bench/client-run-N.json`，连续独立三轮，期间没有并行跑其它验收；测量进程绑定到 P 核（亲和性 0xFFF）并设为高优先级。但本机在测量期间有与 axp 无关的外部负载：一个 `find / -name perf-1080.mp4`（PID 33756，15:10 起持续占满一个核并带来大量磁盘活动）和多个常驻 dev server，CPU LoadPercentage 约 47%。这些进程不是本任务启动的，未处理。结果上：同一个实现的“B2 无插件”与“B2-0 0 层”hz 最多相差约 40%（第 3 轮 22,096 对 30,965），第 1、2 轮 8 层反而比 0 层快，三轮 hz 的最大/最小差在 40%–100% 之间，远超旧基线 10% 的稳定口径。因此下面的三轮表只是按要求留档的记录，**不能据此评价性能，也不能与 B0 做精确对比**。此前一组未绑核的试跑（B1 裸 axios 为 50.5k / 43.9k / 22.4k hz）同样被外部负载污染，已被覆盖。

## 6. AxpRequestOptions 模块扩展

相对路径 declare module 的类型测试通过，retry/cache 示例字段可以在客户端调用处使用，错误写法由 @ts-expect-error + tsgo 验证。旧 axios 模块增强不进入新配置：新类型列出当前 axios 全部原生字段，单独叠加 AxpRequestOptions，排除旧插件选项与 cancelToken。

外部包名形式也已实测：临时入口把同一个 AxpRequestOptions 从 src/types.ts 重导出，并把 @codejoo/axp 映射到该入口；消费端 declare module 扩展新增字段，合法写法通过、错误值报错，独立 tsgo 退出码 0。条件是 B6 正式根入口及声明产物必须重导出这个同一接口，并能被消费者模块解析找到；不能重建一个同名但未连接调用配置的接口。B1 未改 index.ts，所以当前已发布入口还不具备这项新扩展能力。

## 7. 规格不清与保守取舍

1. types.ts 的旧段格式冲突已由本轮第 8 条明确授权解决；本轮八项无未决规格问题。
2. taps 的“序号”未规定起点：使用数组索引，从 #0 开始；handle 与 taps 同时存在时分别参与排序，实例字段覆盖同名的静态字段。
3. dispose 的异常次序及销毁后行为未明确：沿用旧清理的逆序、尽力执行、最后抛首个异常；销毁后拒绝新的 request/use/extend，在途请求沿原链并接收取消 signal。
4. 自定义工厂自己持续抛错时，“next 永不 reject”和“扩展字段始终存在”无法同时由坏工厂保证：最后用内置工厂构造 internal，保留首次程序异常，确保外层收尾，落定抛原异常；此时不能凭空制造自定义 R 的业务扩展字段。已写同步/异步及工厂二次抛错测试。
5. R 的默认类型判断按 TS 结构相等处理；带额外字段的 R 强制匹配工厂。只覆盖 getter 而未增加任何实例字段的子类，与 AxpResponse 在结构类型系统中无法区分。
6. 不可哈希值增加循环祖先检测，返回 null；FNV 两车道、空值过滤、顺序/分帧、采样和二进制长度规则沿用旧算法。用户 getter 的 RangeError 仍原样作为 bug 暴露，不把它误当作循环吞掉。

### 10.2 新增与调整的用例

新增 30 条：key 固定输入快照 23、transport 自身兜底 1、静态非法阶段与重名在 setup 之前被拒绝 1（boundary）、methods 2、utils 2、阶段表顺序 1。调整：taps 用例扩成四种变体、response 用例补显式 `error` 覆盖、上面三条失败用例的断言。测试辅助：`testContext` 增加 `log` 参数，`createTestClient` 说明 `transport` 参数用法。

### 10.3 规模与取舍

行数（精简前 → 现在）：src 六个内核文件 + types 为 2042 → 2126（含新增 methods 13、stages 13、utils 15），测试支撑与用例 2207 → 2485，bench 75 → 120。总行数是增加的：精简前后的代码都经过格式化，精简主要体现在结构上，如每个请求少一次原型链构造、少一层 async 帧与重复 try/catch、状态与 abort 闭包惰性创建、少两处重复补品牌、debug 不序列化成功请求的 stack，以及 key.ts 删掉 `simple` 分支（346 → 318）；同时 `guardFactory` 和 `resolveInit` 写得更显式，复述类注释改写后也不再是模板句，新增用例本身占了大头。这些结构收益的性能影响没有可信的实测（见 §5）。

仍存在的风险：bench 三轮受外部负载支配，需在稳定环境复核；key.ts 还有 2 个不属于门槛的分支未覆盖（见 §8）。
