## 3. 实现核对：对照规格逐条结果

### retry.ts

| 规格要求                                                                                                                         | 结果                                         |
| -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 默认 `max: 2`、指数退避、`delayMax: 10_000`                                                                                      | 符合                                         |
| 判定 6 级：请求级 false → 方法硬否决 → kind 否决 → `shouldRetry` 布尔 → network / timeout → `statusCodes`                        | 符合，顺序由测试逐级固定                     |
| `Retry-After`：仅在 `isRetryAfterEligible` 时采信，`retryAfterMax` 封顶，不叠加 jitter，不受 `delayMax` 限制，头无效回退 `delay` | 符合                                         |
| 先 `markReplayable()` 再循环 `next()`                                                                                            | 符合；突变检查去掉后会被请求体用例拦住       |
| 等待用 `waitFor(ms, ctx.signal)`，取消立即结束，不再进入内层                                                                     | 符合；用「内层进入次数」断言，不止看网络次数 |
| 耗尽返回最后一次 `R`                                                                                                             | 符合                                         |
| `delay` / `jitter` / `shouldRetry` 抛错按 bug 抛原始异常，不遗留定时器                                                           | 符合                                         |
| 请求级：数字 = max、false、true、对象；数组整体替换；非法值按省略                                                                | 符合                                         |

补改：

- **类型错误**：`retryAfterMs(response.raw?.headers, …)` 的参数是 axios 头类型，与 `IRetryAfterHeaders`（全可选的弱类型）无交集，tsgo 报错。在 `retry.ts` 里加了类型断言，没动 `retry-timing.ts`。
- **不可达分支**：`shorthand` 的非数字分支永远走不到（`handle` 只把数字交给它），导致分支覆盖缺 1 处。改成直接取数字，不加忽略标记。
- 文件头加 `no-await-in-loop` 禁用说明：重试必须按序等待和发送。

### auth.ts

| 规格要求                                                                                             | 结果                                                               |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 主流程顺序：未保护 → `markReplayable` → 等刷新 → 本地无 token → `ready` + 记注入快照 → `next` → 路由 | 符合（见下「删除的入口检查」）                                     |
| `defaultAuthFailure` 按状态键判 replay，不解析请求头                                                 | 符合；自定义凭证头也能正确路由                                     |
| 五动作、失败输出 `ctx.fail({ kind: 'auth', reason, from })`                                          | 符合；`from` 保留原 401 / 403 的状态，无 `from` 的合成响应状态为 0 |
| 重放后仍 refresh / replay → 判 expired                                                               | 符合，含自定义 `onFailure` 一直返回 Replay                         |
| 单飞刷新建在 `setup`，每客户端一份                                                                   | 符合；同一插件对象装两个客户端互不阻塞                             |
| 过期每轮只通知一次；O4：记 token 快照，token 未变前不再刷新，登录新 token 自动恢复                   | 符合                                                               |
| 通知类 `fireNotice` 隔离；判定类抛错按 bug；`onRefresh` 抛错 = 刷新失败                              | 符合；通知异常 `console.error` 恰好一次                            |
| 请求级 `protected?: boolean`，非布尔按省略                                                           | 符合                                                               |

补改：

- **删除入口处的 `isExpired()` 检查**：Codex 在「正在刷新」之后、「本地无 token」之前多加了一步「已过期则直接 `auth/expired`」。规格主流程里没有这一步，而且它会让过期后（token 已清空）的新受保护请求拿到静默的 `expired`，永远走不到规格写明的「本地无 token → `onAccessDenied` + `unauthenticated`」。过期状态仍在路由分支里生效（`replayed || isExpired()`），O4 行为不变。
- **新增 debug 日志**：`onRefresh` 抛错按失败处理，但原先完全静默，业务方写错刷新函数时无从排查。现在 debug 开启时 `ctx.log.warn` 一条（关闭时零开销）。规格没写，不改变行为。
- 文件头加 `no-await-in-loop` 禁用说明：刷新后的重放必须按序执行。

### TokenManager.ts

`ITokenManager` 和默认实现删除 `canRefresh`，其余行为不变；删除后遗留的多余空行已清理。

### 测试侧发现：axios 会浅拷贝请求体

写 I7（每次尝试请求体一致）用例时，最初用 `{ n: 0 }` 加原地改入参的 `transformRequest`，结果去掉 `markReplayable()` 后测试仍通过。原因是 axios 的 `mergeConfig` 本身就会拷贝顶层普通对象。改用嵌套数组 `{ items: [{ n: 0 }] }`（axios 只浅拷贝数组，元素共享）后，去掉 retry 或 auth 的 `markReplayable()` 都会被拦住。这说明内核按需 `structuredClone` 确实在起作用，没有发现内核 bug。

## 7. 保守取舍与规格不清

规格不清、按最保守理解实现的地方，需要主会话确认：

1. **过期后的新请求会再次触发 `onAccessExpired`（建议主会话确认）**。规格写「本地无 token → `onAccessDenied`」，又写「`onAccessDenied` 缺省回退 `onAccessExpired`」，过期时会 `tm.clear()`。于是没配 `onAccessDenied` 的用户，在登录前每发一个受保护请求都会再触发一次 `onAccessExpired`。这和旧版行为一致，「每轮只通知一次」只约束同一轮 401 / 刷新失败那条路径。如果要对本地拒绝也去重，需要改规格，不是实现问题。
2. **`shouldRetry` 对成功响应也会被调用**。规格判定顺序没写 `r.ok`，旧行「成功响应被判为业务异常时也触发重试」要求保留这个能力。默认规则下成功响应不重试。
3. **`onFailure` 不接收 `internal` 和 `cancel`**。规格主流程只写「`r.ok` 则返回」，但这两类一个是 bug、一个是取消，交给路由没有意义；`network` / `timeout` / `parse` 仍交给 `onFailure`，默认判 Others。
4. **`isProtected` 每次尝试入口求值一次**。auth 在 retry 之内，retry 的每一轮都会重新进入 auth；重放（刷新后再发）不重复求值。迁移表旧行写「prepare 之后只判一次」，要做到跨重试只判一次需要新增状态键，没有加。
5. **刷新不随取消中止**。发起者或等待者取消，只让自己以 `cancel` 结束；`cancelAll` 后刷新仍会跑完：成功则新 token 写入会话，失败则清会话并通知一次过期。
6. **`onRefresh` 抛错**：不当 bug，也不抛出；debug 开启时才有一条 `ctx.log.warn`。
7. **`retry` 的 `max` 为 0 或负数时仍调用 `markReplayable()`**，只多一次请求体克隆，没有为此多加分支。`max` 为 `Infinity` 会一直重试到成功，没有保护。
8. **O4 的快照是 `tm.accessToken` 的当前值**（默认实现含 `Bearer ` 前缀），只做相等比较。
9. **`retry-timing.ts` 的 `IRetryAfterHeaders` 是弱类型**，与 axios 头类型无交集，`retry.ts` 里用断言绕开，没有改纯算法模块。
